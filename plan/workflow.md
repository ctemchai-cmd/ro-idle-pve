# วิธีจัดการงานด้วยไฟล์

ตามรูปแบบที่ผู้ใช้กำหนด: `overview.md` ติดตามภาพรวม และย้ายไฟล์เดียวระหว่าง `todo/`, `inprogress/`, `review/`, `done/` เพื่อเปลี่ยนสถานะ

## เอกสารกับงาน

- `design/`: รายละเอียดระบบเกม แยก “ยืนยัน”, “เสนอ”, “รอตัดสินใจ”
- `decisions.md`: ข้อสรุป เหตุผล และคำถามค้าง
- `task-template.md`: หัวข้อร่วมของงานออกแบบ/พัฒนา/ตรวจรับที่จะเพิ่มบนกระดาน
- `overview.md`: ความคืบหน้า milestone งานปัจจุบัน และลิงก์เอกสาร
- โฟลเดอร์สถานะทั้งสี่: เก็บเฉพาะงานจริงตามชื่อ `tasks_001.md`, `tasks_002.md`, ...

ID และชื่อไฟล์ task คงเดิมเมื่อย้าย อ้าง dependency ด้วย ID เช่น `TASK-001` เพราะพาธเปลี่ยนตามสถานะ ไม่เขียน status ซ้ำใน frontmatter ให้ขัดกับโฟลเดอร์ แต่ละ ID มีไฟล์เดียวทั้งกระดาน

รุ่นแรกมี TASK-001–047: M0 จำนวน 15 งานเป็นการออกแบบข้อมูล/สเปกและตรวจรวมก่อน coding (TASK-047 อยู่หลัง TASK-002 ก่อนข้อมูลสกิล/ไอเทม) งานพัฒนา TASK-015–046 ต้องผ่าน TASK-014 ก่อน การสร้างรายการงานยังไม่เริ่มทำงานจริง เริ่ม TASK-001 เมื่อผู้ใช้สั่งเริ่มตามแผน

ก่อนเริ่ม task ค้น ID ที่ต้องรอในทั้งสี่โฟลเดอร์ ตรวจว่าอยู่ done ครบ แล้วอัปเดต overview ตามไฟล์จริง ระบุเกณฑ์เป็น AC-01 เป็นต้นและเก็บหลักฐานต่อข้อ ไม่ใช้การนับจำนวนไฟล์หรือการสร้างเอกสารแทนผลตรวจรับ

## การไหลของงาน

1. เข้า `todo/` เมื่อมีผลส่งมอบ ขอบเขต ขั้นตอน และเกณฑ์ตรวจรับที่ตรวจได้จริง ระบุ dependency เป็น ID หรือ “ไม่มี”
2. เข้า `inprogress/` เมื่อ dependency ที่ต้องรออยู่ `done/` ครบแล้ว และข้อสงสัยที่จำเป็นต่อการทำงานมีข้อสรุป ค่าเริ่มต้นคือทำงานหลักครั้งละหนึ่ง task
3. เข้า `review/` เมื่อผลส่งมอบพร้อมตรวจ แนบไฟล์ที่เปลี่ยน วิธีทดลอง ผลตรวจ และข้อจำกัด
4. เข้า `done/` เมื่อเกณฑ์ตรวจรับผ่านครบทุกข้อ มีหลักฐาน และบันทึกผู้ตรวจ/วันที่ งานที่ “ยังตรวจไม่ได้” ยังไม่ผ่าน
5. Review ไม่ผ่านให้กลับ `inprogress/` โดยใช้ ID เดิม บันทึกข้อที่ไม่ผ่านและผลตรวจรอบใหม่
6. ถ้าทำต่อไม่ได้เพราะ blocker ภายนอก ให้บันทึกสิ่งที่รอและกลับ `todo/` เมื่อหยุดทำงานนั้น ไม่เพิ่มโฟลเดอร์สถานะใหม่โดยจำเป็น
7. อัปเดต `overview.md` หลังย้าย รวมถึงลิงก์ที่เปลี่ยนพาธ

การ review อาจใช้การอ่านงาน การทดลองใน browser หรือตัวจำลอง/การทดสอบตามลักษณะงาน ระบุผู้ตรวจจริง ไม่สมมติว่าผู้ใช้ยืนยันแล้วหากยังไม่ได้ตอบ

## ความพร้อมของรายละเอียดก่อนลงมือ

M0 เป็นงานออกแบบที่ยังต้องผลิตข้อมูลจริง งาน implementation ใช้ผลที่ผ่าน TASK-014 แล้ว ก่อนย้ายไป inprogress ต้องรู้ input/ข้อมูลอ้างอิง ผลคาดหวัง และวิธีตรวจครบทุกเงื่อนไขย่อยของ AC งานที่จำเป็นต้องใช้ตัวเลขต้องอ้างตารางหรือ budget ที่มีอยู่จริง ไม่กำหนดว่า “เร็วพอ/สมดุลดี” โดยไม่มีเกณฑ์

TASK-014 จัดทำ `plan/acceptance-matrix.md` ผูกทุก AC กับ case ID/ข้อมูลตั้งต้น/ผลคาดหวัง/วิธีวัด โดย M0 ใช้การอ่าน/คำนวณได้ ไม่ต้องรอ runner ที่ยังไม่สร้าง เมื่อ tooling พร้อมจาก TASK-015 ให้บันทึกคำสั่งจริงที่ใช้ในแถวหลักฐานแต่ละข้อ การลองเคสเดียวไม่ทำให้เงื่อนไขย่อยอื่นผ่านไปด้วย

[Architecture audit](architecture-audit.md) ระบุ A-01–A-08 ที่ต้องมี decision/contract/ตัวอย่างและเจ้าของการทดสอบก่อน TASK-014 ผ่าน จากนั้นพิสูจน์ boundary/replay/parity เมื่อมีแกน และพิสูจน์ save/retry/AFK/migration ก่อนตรวจรับรุ่น การตรวจ dependency หรืองานออกแบบผ่านไม่ใช่หลักฐานว่า runtime ผ่านหรือไม่มี technical debt

งานช่วง vertical slice ตรวจส่วนพื้นฐานที่กำหนดใน scope ส่วนความครบทุกอาชีพ/ทุกด่านตรวจที่งานอาชีพ TASK-029–034 และรวมที่ TASK-041/044 ไม่เพิ่ม dependency ย้อนจน UI ต้องรอสกิลทุกอาชีพในขณะที่งานสกิลนั้นต้องรอ UI

## ขนาดและการเปลี่ยนแผน

หนึ่ง task ควรมีผลลัพธ์ที่ตรวจรับแยกได้ เช่น “ร่ายพร้อมกันสองฝ่ายและขัดร่ายได้” งานใหญ่ให้แบ่งตามพฤติกรรมที่สาธิตได้ เลี่ยงการรวมทั้งระบบอาชีพทั้งหมดไว้ในไฟล์เดียว

คุยแผนทั้งหมดก่อนเริ่มลงมือ แต่เมื่อลองจริงพบสมมติฐานผิด ให้แก้ design/decisions และ task ที่ได้รับผลก่อนทำต่อ ตัวเลขบาลานซ์เป็นค่าตั้งต้นสำหรับวัดผล

ถ้าเปลี่ยนความต้องการหลัง done ให้สร้าง task ใหม่อ้างงานเดิม ถ้าพบว่างานเดิมไม่ผ่านเกณฑ์ที่รับไว้จริง สามารถเปิดงานเดิมกลับมาพร้อมเหตุผล ห้ามแก้เกณฑ์ย้อนหลังเพื่อให้ข้อที่ตรวจไม่ผ่านดูเหมือนผ่าน
