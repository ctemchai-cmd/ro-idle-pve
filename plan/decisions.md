## แบบทางเทคนิคที่ปรับในรอบ D-036

ใช้ [extension contracts](design/14-extension-contracts.md) และ [ตัวอย่างประกอบ](examples/composition-contract.json) เป็นฐานออกแบบ ไม่ใช่ user-confirmed schema หรือผลทดสอบ engine:

- Ordered typed effects/target bindings/outcomes ต่อเป้า ใช้ร่วมสกิล/Passive/ไอเทม/การ์ด พร้อม registry สำหรับสูตรและกลไกเฉพาะ
- Immutable definitions → build variant ที่ patch ด้วย stable effect ID → battle instances; ไม่แก้ shared base หรืออ้าง array index
- Modifier buckets/status instance policies/trigger lifecycle แยกชัด; actor collection แยกจาก party validation และ item instance แยกจากการพัฒนา slot
- ตรวจ unknown refs/params, incompatible outcomes, patch conflicts และ proc loops ไม่ปล่อยให้ effect ใหม่ผิดเงียบ
- เลือกฐาน Vercel API รัน account commands ด้วย TypeScript domain ร่วมกัน และให้ Supabase commit/revision/receipts แบบ atomic ไม่แยกสูตรบาลานซ์อีกชุดใน SQL; ต้องลงรายละเอียด/ตรวจใน TASK-013 ไม่ใช่บริการที่สร้างแล้ว

ส่วนที่ไม่ต้องถามผู้ใช้ให้เลือกระดับ implementation: paths/modules, event/cancellation IDs, serialization, API shape, migration mechanics, quality tooling และตาราง baseline ที่ผู้ช่วยต้องออกแบบพร้อม expected cases ใน M0 ส่วนกติกาเล่นที่เปลี่ยนประสบการณ์ต้องแสดงเป็นข้อเสนอจนได้ข้อสรุป

TASK-001 ส่ง [release scope](design/09-release-scope.md) และ [progression](data/progression.json) ที่ผ่าน self-review พร้อมหลักฐานแล้ว ตัวเลขที่ผู้ช่วยเลือกเป็น baseline ได้แก่ base stats1, 5แต้ม/เลเวล, ต้นทุนเลเวล/Breakthrough, skill cap formula, ตารางปลดระบบ และ actual-paid refund policy ไม่ใช่ตัวเลขที่ผู้ใช้ระบุเองหรือ balance ที่ผ่าน simulation; TASK-010/011/041 ต้องตรวจ pace/encounters ต่อ
