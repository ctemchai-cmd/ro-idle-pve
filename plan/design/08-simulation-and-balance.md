## สัญญาของ combat engine

- ใช้กติกาเดียวกับเกมจริง แยก engine จาก Canvas/DOM/เสียง/Supabase/เวลาเครื่อง
- รับสถานะเริ่มต้น: ทีมและศัตรู, level/Status, สกิลและคิว, อุปกรณ์/Refine/Enchant/การ์ด, กติกาโหมด, รุ่นข้อมูล และ seed
- ฉีด clock และ RNG เข้า engine; การเดินเวลาไม่ใช้ `Date.now()`, `Math.random()`, `setTimeout` หรือ FPS โดยตรง
- จัดเหตุการณ์ตามเวลาเกมและลำดับกรณีเวลาเดียวกันที่ระบุใน combat spec รองรับเดินถึงเหตุการณ์ถัดไปจนจบไฟต์ โดยไม่รอวินาทีจริง
- เกมจริงเลือกวาดตามเวลาที่ผ่านไป ส่วน runner เดินเวลาเสมือน ผลที่ใช้ seed/input เดียวกันต้องตรงกัน
- สถานะจบและตัวเลขผลต่อสู้ต้องอ่านได้โดยไม่เปิด renderer; การเก็บ event log แบบละเอียดเปิดเฉพาะตอนวิเคราะห์เพื่อลดต้นทุน batch
- มีเพดานเวลาเกม/จำนวนเหตุการณ์และการตรวจค่าผิดปกติ ป้องกัน proc วนไม่จบหรือช่วงเวลาเป็นศูนย์จน runner ค้าง

API ตัวอย่างเพื่อใช้ทำสเปก ไม่ใช่ implementation ที่เสร็จแล้ว:

```ts
simulateBattle({ scenario, content, seed, limits, trace }): BattleResult
runBatch({ scenarios, seeds, variants, metrics }): BatchReport
```

`BattleResult` และ `BatchReport` ต้องเป็นข้อมูลที่ serialize ได้ มี schema version, content version/hash, rules version ที่ครอบคลุมสูตร/ลำดับเหตุการณ์/RNG และ replay inputs เพื่อย้อนหากรณีผิดปกติได้ ห้ามให้ runner มีสูตรดาเมจหรือกติกาสกิลอีกชุดที่ต่างจาก runtime

Replay ต้องเลือกข้อมูล/กติกาตรงรุ่น หรือแจ้ง incompatible ชัดเจนเมื่อไม่รองรับ ห้ามแทนด้วยรุ่นล่าสุดเงียบ ๆ ไม่บังคับเก็บ runtime ทุกเวอร์ชันตลอดไป; TASK-013 ต้องกำหนดช่วงรองรับและ migration/rejection policy ส่วน snapshot ที่ resume กลางไฟต์ต้องระบุ game clock/RNG state/pending events ให้ครบ

Content definition ต้อง immutable และแยกจาก character/build/battle instances เพื่อให้ A/B หรือ Artifact/Awaken ในอนาคตไม่เปลี่ยนสกิลต้นแบบร่วมกัน กติกาทีม main+NPC3 ตรวจที่ party validation ส่วน battle actor collection ต้องรองรับ owner/source/lifecycle ของ Plant/Pet โดยไม่ฝังจำนวนสี่ไว้ใน combat loop ทั้งนี้ยังไม่เพิ่มระบบ Pet เข้ารุ่นแรก ดู A-04/A-07 ใน [architecture audit](../architecture-audit.md)

## สิ่งที่วัด

| กลุ่ม | ตัวชี้วัด |
| --- | --- |
| ผลทีม | ชนะ/แพ้/หมดเวลา, เวลาจบไฟต์, จำนวนผู้รอด, HP/SP คงเหลือ |
| ผลแต่ละ actor | ดาเมจ, DPS, ฮีลที่ได้ผลจริง/overheal, ดาเมจที่รับ, การตาย, shield/ป้องกัน/redirect ที่ช่วยทีม |
| ผลแต่ละสกิล | เริ่มร่าย/สำเร็จ/ถูกขัด/ข้ามเพราะ SP, เป้าที่โดน, ผลตรง/DoT/proc, ประสิทธิภาพต่อ SP และเวลา |
| สถานะและจังหวะ | buff/debuff uptime, เวลาถูก CC, จำนวนขัดสำเร็จ, ช่วง SI/CT/ACD และคิวที่ใช้จริง |
| คุณภาพ runner | จำนวนเหตุการณ์, เวลาที่ใช้จริง, fights/second, จำนวนกรณีผิดปกติและ seed ที่ทำซ้ำได้ |

บัฟ/debuff ของเพื่อนมีผลต่อดาเมจทั้งทีม ไม่ยกดาเมจที่เพิ่มขึ้นทั้งหมดให้ support โดยอาศัยการเดา ใช้การเทียบ A/B ที่ควบคุมเงื่อนไขและรายงานผลทีมร่วมด้วย

## วิธีเปรียบเทียบ

1. กำหนดกลุ่มเลเวล/ทรัพยากร/อุปกรณ์ที่เท่ากัน และยึดข้อห้าม NPC ซ้ำ Class 1 ตามเกมจริง
2. มีหลายโจทย์: เป้าเดียว, หลายเป้า, รับดาเมจกายภาพ/เวท, ไฟต์ยาว/SP, ขัดร่าย, บอสต้าน CC และดันหลายหลอด ไม่ตัดสินทุกอาชีพจาก dummy ตัวเดียว
3. เปรียบเทียบเปลี่ยนหนึ่งปัจจัย เช่น coefficient ของสกิลหรือหนึ่งช่องคิว โดยใช้ชุด seed เดียวกันทั้งสองฝั่ง เก็บรุ่นข้อมูลก่อน/หลัง
4. รายงานจำนวนตัวอย่าง ค่าเฉลี่ย/มัธยฐาน การกระจายและช่วงความไม่แน่นอนที่เหมาะสม ไม่สรุปว่าเก่งเกินจากไฟต์เดียวหรือความต่างเล็กน้อยที่ยังแยกจากความสุ่มไม่ได้
5. ตรวจบทบาทด้วย: Priest ไม่ต้องชนะ DPS ของ Assassin แต่ต้องช่วยอัตรารอด/อัตราชนะได้ตามงบลงทุน ข้อเสนอปรับสมดุลต้องบอกสถานการณ์ที่ดีขึ้นและสิ่งที่เสีย
6. runner เสนอ/รายงานค่าที่น่าตรวจ ไม่แก้ไฟล์บาลานซ์ที่เกมใช้อยู่หรือเซฟจริงอัตโนมัติ

D-037 กำหนดให้บัฟจากหลายตัวบวกกันไม่มีเพดาน เพิ่ม A/B ทีม support หนึ่งตัวกับสองตัวที่งบเท่ากัน เทียบคิวที่บัฟทับเวลาช่วงดาเมจกับคิวที่หลุด uptime วัดทีม DPS/เวลาจบ/รอด/SP และดาเมจที่เสียจากการเปลี่ยนสมาชิก ไม่ตัดสินว่าสมดุลจากการมี trade-off อย่างเดียว และไม่แก้ด้วย cap/diminishing returns ใน buff aggregation โดยไม่เปลี่ยน decision

D-038 คนเดิมร่ายซ้ำเพิ่มชั้นแยกอายุ จึงรายงานจำนวนชั้น/magnitude ตามเวลาและผลเมื่อ cast cycle สั้นกว่าระยะบัฟ ไม่ใช้ uptime อย่างเดียวจนมองข้ามหลายชั้น ทดสอบว่า instance เก่าหมดเวลาเดิม แม้ source actor/skill/status ID ตรงกับชั้นใหม่

## ขอบเขตรุ่นแรกกับส่วนต่อยอด

รุ่น Class 2 ต้องมี engine แบบ headless, replay ที่ทำซ้ำได้, runner ผ่านคำสั่งสำหรับชุดตัวอย่าง/หลาย seed และผลลัพธ์ JSON/CSV ที่อ่านเปรียบเทียบได้ ใช้พิสูจน์กติกาใน M1 และปรับเนื้อหาใน M4 ไม่ต้องรอทำ dashboard ก่อนใช้วัดผล

เตรียม interface สำหรับ progression simulation: สถานะบัญชีเริ่มต้น + ตารางรางวัล/ค่าอัปเกรด + เวลาเสมือน + policy การใช้ทรัพยากร/เลือกด่าน → ประวัติทรัพยากร เลเวล ด่าน และเวลาถึงเป้าหมาย ให้กติกาฟาร์ม/อัปเกรดเรียกเป็น pure calculation ที่ไม่ผูกฐานข้อมูลได้ ใช้ฐานสูตรเดียวกับเกมและตรวจการไม่รับช่วงเวลาเดียวกันซ้ำ

ระบบจำลองผู้เล่นตลอดหลายวัน, parameter sweep ขนาดใหญ่, ค้นบิลด์อัตโนมัติ และ dashboard เป็นส่วนต่อยอด ยังไม่สร้าง AI ที่หาวิธีเล่นเหมาะสมที่สุดในรุ่นแรก ระหว่างนั้นตรวจ pace ด้วยตารางและ batch fight ที่มีบิลด์ตัวอย่างกำหนดไว้

## เกณฑ์สถาปัตยกรรมและหลักฐานที่ต้องมี

- import engine/runner ใน process ที่ไม่มี browser และไม่มี network ได้
- input/seed เดียวกันให้ผลและ event order ตรงกันเมื่อเปลี่ยนความถี่การวาดหรือรันเร็วโดยไม่วาด
- รายงานของ actor/skill รวมกลับเป็นผลไฟต์ได้ ไม่คิด overheal เป็นฮีลที่ช่วยชีวิต ไม่คิด cast ที่ถูกขัดเป็นดาเมจสำเร็จ
- เคสผิดปกติใน batch คืน seed/input ที่ replay ได้ พร้อม schema/content/rules versions; คนตรวจไม่ต้องเดาจากภาพ
- วัด throughput ด้วย scenario และเครื่องที่ระบุ ไม่อ้างว่าเร็วได้กี่เท่าก่อน benchmark
- การรัน balance simulation ไม่เขียนเงิน/ของ/เซฟจริง และไม่เรียกบริการ cloud

กระจายงานนี้ใน M0 สเปกต่อสู้/ข้อมูล/สถาปัตยกรรม, M1 engine/runner และ M4 วัดบาลานซ์ ดู [overview](../overview.md) และ [combat spec](02-combat-and-skills.md)
